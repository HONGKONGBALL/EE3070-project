## 8 秒之后到底会怎样

8 秒是同类别提醒的最短间隔，不是定时重复播报开关；冷却期间仍继续识别。只有新／重新建立的目标仍在前方、满足连续两次确认且证据新鲜，才会生成新事件。

| 情形 | 当前代码行为 |
|---|---|
| 同一个已提醒目标连续保留超过 8 秒 | 不会仅因为到时而再次提醒 |
| 新的同类目标在 8 秒之后出现并确认 | 可以再次提醒 |
| 新的同类目标在冷却内出现，一直留到冷却结束 | 冷却结束且条件仍有效时可以提醒，不需从该目标出现再额外等 8 秒 |
| 新目标在冷却内出现又离开 | 不在之后补报已离开的目标 |
| 不同类别，例如积水之后出现楼梯 | 不共用同一类别的 8 秒冷却，但仍受自身确认和声音队列控制 |

四个确定性逻辑检查已通过，见 `cooldown-policy-check.json`。该记录只测试当前策略，输入是明确标记的人工观测记录，不冒充真实水坑视频。

真实步行视频中目标 ID 会因为机位移动、分割框与分类观察区切换而重建。因此，即使人看到的仍是同一段楼梯，程序可能在 8 秒后把它当作新目标重新提醒；也可能一直跟踪同一个目标而保持安静。当前不是一致的“持续危险每 8 秒提醒一次”。

## 如何理解结果与边界

- 林间视频的积水事件按冻结的“无明显路面积水”标签计作误报，证据帧另存为 `forest-puddle-event-evidence.jpg`。不能把此前图片负例通过当作移动视频也通过。
- 本轮没有满足要求的连续水坑步行正例。下载的一段 Pexels 素材标题虽写 walking，实际前半段主要是原地踩水，已排除；不拿它验证持续向前行走。本轮不声称已验收步行水坑或坑洞的正例能力。
- 稀疏窗口只标记能确认类别的片段；未定过渡不计分。早于窗口已提醒的目标可能继续去重，不能把窗口内无新事件直接当作模型漏检。没有逐帧框／目标身份真值，不报告总体准确率或 mAP。
- 视频秒数是截取片段时间；程序的冷却使用实际运行时钟。Windows 回放会略慢于原片，表中实际间隔直接来自事件时间，不把视频时间差当成 8 秒的精确验证。所有原片运动顺序与原时间采样保持不变。
- 启动时的帧率统计曾出现相同时间戳导致的除零错误；加入了一个常数开销保护，仅用于状态统计。模型、阈值、跟踪、8 秒规则均未改；首次失败记录保留为 `initial-startup-error.txt`，相同冻结输入与标签重新运行。该状态保护未热更新到 Pi。
- 结果视频来自实际程序预览，框不等于已提醒；事件不等于耳机发声。当前音频关闭，实际行走时的提前量仍未验收。
